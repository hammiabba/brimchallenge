# Design decisions

One line per decision: **what** and **why**. Add to this file when you make a choice someone could ask about in the Q&A.

| # | Area | Decision | Why |
|---|---|---|---|
| 1 | Stack | FastAPI + Pydantic v2 | The contract is already Pydantic; FastAPI gives typed endpoints, `/docs` for free, and an OpenAPI spec to generate frontend types from. |
| 2 | Stack | One `backend/pyproject.toml` with a `[dev]` extra | A single source of dependencies; `pip install -e "backend[dev]"` works the same for all four of us. |
| 3 | Extraction | LLM maps text → fields, then deterministic code normalizes and self-checks | Templates/regex break on the hidden batch's unseen layouts. The LLM handles layout; code handles maths, and maths is checkable. |
| 4 | Extraction | The LLM returns values **as printed** (strings); Python parses money/dates into `Decimal`/`date` | Keeps the LLM from "helpfully" rounding or fixing numbers, and puts parsing in tested code. |
| 5 | Extraction | Structured outputs with a Pydantic schema (`messages.parse`) | Output always matches the schema; no fragile JSON-in-text parsing. |
| 6 | Extraction | Keep printed values even when the maths is wrong; record a warning | Wrong vendor maths is a finding for controls (TOTAL_MISMATCH, LINE_MATH_ERROR), not something to hide. |
| 7 | Extraction | Disk cache keyed by sha256(file) + prompt version + model | Reruns are free and deterministic for the demo; changing the prompt invalidates automatically. |
| 8 | Extraction | Text layer first, OCR if under ~50 meaningful chars, vision LLM if OCR is unavailable | The cheapest reliable source first; scans still work on a machine without tesseract. |
| 9 | Extraction | OCR fixes only on structured IDs (GST no., transit, account), each logged as a warning | Those have known shapes, so a fix is verifiable; free text is never "corrected". |
| 10 | Vendor | Match order: GST number → bank account → sender domain → fuzzy name ≥ 90 | The master has lookalikes (V026/V052, V002/V053). Names are the weakest evidence, so they come last, and the method is recorded. |
| 11 | Intake | Rules-first email classifier with EN+FR keywords; LLM only as a tie-break | Deterministic and explainable for the common cases; subject and body can be in different languages, so both are scored. |
| 12 | Coding | Vendor history → vendor default GL → global description similarity | History is the best predictor of how this company codes a vendor; each tier lowers confidence and says why. |
| 13 | Data | `ReferenceRepository` Protocol with a CSV implementation | Person A can build now without waiting for the DB; the DB team swaps in a SQL-backed class without touching callers. |
| 14 | Money | `Decimal` everywhere | Float rounding errors make arithmetic checks and duplicate matching unreliable. |
| 15 | Time | Fixed `AS_OF_DATE` from config | The dataset is frozen at 2026-11-02; using the real clock would make results drift. |
| 16 | Intake | Pipeline returns an `ExtractionOutcome` wrapper (ok / llm_skipped / failed) | `DraftBill` requires an invoice number and date, so a failed or skipped extraction can't be a DraftBill; no schema change needed. |
| 17 | Extraction | The LLM fills a union-free `WireInvoice` (plain strings, `""` = not printed); `to_raw()` converts it to `RawInvoice` (`None` = absent) | Structured outputs reject schemas with more than 16 union-typed parameters (we had 23 → HTTP 400). Keeping `None` inside the app means normalize/pipeline/cache don't change, and the wire schema has headroom for new fields. A test guards the count. |
| 18 | DB | Money as INTEGER cents (`*_cents`) beside `currency`; rates, quantities and unit prices as exact-decimal TEXT | SQLite stores `Numeric` as float; cents and text keep money and rates exact. |
| 19 | DB | Timestamps stored as naive UTC; an ORM hook converts aware datetimes | SQLite drops the offset silently (15:00-05:00 is stored as 15:00). |
| 20 | DB | One `bills` table for history and app bills, IDs continuing `AP-#####`; no UNIQUE on (vendor, invoice number) or `payments.bill_id` | The duplicate checks must see the history's repeats: 5 repeated numbers, 3 double payments. |
| 21 | DB | Named CHECK constraints through a naming convention | Errors name the rule that failed, and SQLite batch migrations can only alter named constraints. |
| 22 | DB | `audit_events` is append-only via BEFORE UPDATE / DELETE triggers, with an AUTOINCREMENT `seq` and no FK or CHECK on the actor | The database itself guarantees the log can't be rewritten, and it never rejects an event. |
| 23 | DB | Vendor bank details versioned in `vendor_bank_accounts`, with a partial unique index allowing one open account per vendor | Bank changes are controlled actions, and each payment records which version it paid. |
| 24 | DB | users ↔ departments foreign keys are deferrable; the baseline is SQLite-only | The cycle needs deferred checks to seed. A Postgres port needs its own trigger and a separate FK step. |
| 25 | DB | Separation of duties also enforced as CHECKs: bank-change verifier ≠ requester, payment releaser ≠ preparer, delegate ≠ actor | Defense in depth under the controls rules. |
| 26 | DB | Relative SQLite URLs resolve against the repo root | `.env.example`'s `./backend/ap.db` then works from any working directory. |
| 27 | DB | `bills.draft_json` is the frozen extraction snapshot; the current bill state is rebuilt from columns and line tables | Corrections stay auditable as 'extracted vs corrected'; one source of truth for controls input. |
| 28 | DB | `approval_decisions` stores both `actor_role` (user role) and `step_role` (route step) | The dataset uses step names as roles; one mixed column would make role queries ambiguous. |
| 29 | DB | The seed is insert-only: ON CONFLICT DO NOTHING on the primary key, natural-key checks for autoincrement tables | A re-seed never overwrites app edits to vendors, users, policies or bills; a second run inserts 0 rows. |
| 30 | DB | The seed pre-flight checks every row against rules read from the schema (NOT NULL, CHECKs, FKs) and writes nothing if any fails | Every violation is reported at once, and the Python rules can't drift from the migration. |
| 31 | DB | Money with more than 2 decimals is rejected at seed time, never rounded | Silent rounding would change amounts that controls checks to the cent. |
| 32 | DB | History `bill_taxes` built with controls' `_history_taxes`, and `norm_invoice_number` with `norm_invoice_no` | The database and the controls engine agree on tax codes and duplicate keys by construction. |
| 33 | DB | History `actor_role` taken from users.csv at seed time | approvals.csv records only the step name; the user's role at the time isn't in the dataset. |
| 34 | DB | BC-009 seeded as `pending_verification` while V004's open account is already the new one | That's what happened: the change was applied without a callback, which is exactly what controls must flag. |
| 35 | DB | `log_event` writes inside the caller's transaction (SAVEPOINT) and never commits | A state change and its audit event commit or roll back together: no orphan events, no unaudited changes. |
| 36 | DB | Audit events are hash-chained (`prev_hash` → `hash`, first = "GENESIS"), with a UNIQUE index on `prev_hash` | `verify_chain` detects any edit, insertion or deletion in the middle, and the chain can never fork. |
| 37 | DB | SQLite transactions use SQLAlchemy's pysqlite recipe (driver autocommit off, BEGIN emitted explicitly); write sessions use BEGIN IMMEDIATE | SAVEPOINT release can no longer commit by itself, and writers take the lock before reading, which avoids immediate 'database is locked' errors in WAL mode. |
| 38 | DB | Bank account numbers in audit payloads become last 4 plus HMAC-SHA256 fingerprint keyed by AUDIT_HMAC_KEY; digit runs of 7+ in comments are masked | An unsalted hash of a 9-digit number is brute-forceable; the HMAC still matches mentions of one account. |
| 39 | DB | Audit values are normalized before hashing (Decimal as exact strings, UTC ISO timestamps with Z, sorted sets, canonical JSON) | An event hashes the same at insert and when recomputed from the database. |
| 40 | DB | The audit CSV export streams in 500-row keyset batches and prefixes formula-like cells with `'` | Exports of any size use flat memory, and opening one in a spreadsheet can't run injected formulas. |
| 41 | DB | Audit reads return `AuditRecord` (`schemas.AuditEvent` plus `seq`, `request_id`, `prev_hash`, `hash`) | Keyset pagination needs `seq`; a subclass extends the contract without changing `schemas.py`. |
| 42 | DB | log_event refuses to run on a read session | Every audited write must hold the write lock; misuse fails loudly in development. |
| 43 | DB | chain_head() exposes the newest (seq, hash) for export anchoring | verify_chain cannot detect deletion of the newest events; an anchor kept by the auditor can. |
| 44 | DB | Correction to row 37: the recipe sets the sqlite3 driver's isolation_level to None (driver autocommit, implicit BEGIN disabled) so SQLAlchemy emits BEGIN / BEGIN IMMEDIATE itself; row 37's 'driver autocommit off' is inverted | Keeps the decision log accurate; the log is append-only. |
| 45 | API | Session is an HMAC-signed cookie (stdlib), holding only the user id; the user row is re-read on every request | No new dependency; a role change or termination applies on the next call; nothing in the cookie grants permissions. |
| 46 | API | Role checks only in `require_role`; object scope only in `app/services`; out-of-scope objects return 404 | One place to audit each kind of rule, and a 404 doesn't reveal that a bill in another department exists. |
| 47 | API | Every endpoint is in a hand-written permission matrix, and a test fails if an OpenAPI operation has no row or answers without a session | A new route can't ship without an explicit role decision. |
| 48 | API | Money crosses the API as strings ("742.30"); JSON numbers are refused for money fields | A float can't hold most cent amounts exactly; strings round-trip through Decimal and integer cents without loss. |
| 49 | API | CSRF: SameSite=Lax cookie plus an Origin allowlist on POST/PUT/PATCH/DELETE | Lax alone doesn't help across localhost ports (same site); the Origin check does, with no token plumbing. |
| 50 | API | The intake router is guarded at mount time in `main.py`; employees submit via `/submissions` | Keeps the intake lane's file unchanged and all role rules in the API lane. |
| 51 | Intake | Every triaged email gets a suggested action (create drafts / request resend / answer status / reconcile later / ignore); payment inquiries are answered from `invoices.csv` + `payments.csv` | A clerk acts on non-invoice mail instead of just seeing a class. The vendor must be identified from the sender first, so an invoice number shared by two vendors never answers for the wrong one. |
| 52 | Extraction | Ambiguous slash dates ("03/04/2026") keep both readings; the due date, payment terms, the other date's format and the as-of date settle them, otherwise day-first with low confidence and a warning | Silent guessing would put wrong dates into duplicate and FX checks; evidence on the page usually decides it. |
| 53 | Extraction | File type is sniffed from the first bytes before any parsing; unreadable files fail with one plain-English sentence | A renamed .docx or a locked PDF must not surface as a stack trace, and a scan saved as .pdf is still readable. |
| 54 | Extraction | Several invoice numbers on separate pages → warning and lower confidence, never a silent merge or split | Splitting needs a human to confirm page boundaries; merging would hide an invoice. |
| 55 | Extraction | Document text is fenced in `<document>` tags it can't close; the prompt says it is data; the schema has no vendor id, status or approval field | Prompt injection in an invoice can at most change a printed value, which the deterministic vendor match and controls then check. |
| 56 | Intake | The same file (sha256) received twice links to the bill it already made; voided bills don't count | Transport repeats aren't business duplicates; controls' DUPLICATE_* flags still catch a different file for the same invoice. |
| 57 | Coding | A clerk's accepted/overridden coding on a near-identical line from the same vendor wins the next suggestion and is named in the reason | The company's newest decision beats older history, and the clerk can see why the suggestion changed. |
| 58 | API | Person A's behaviour reaches the DB lane's services through single-call hooks (see `docs/ISSUES_FOR_DB.md`), not a parallel draft API | One clerk-review path (`/bills`) for the frontend; the logic stays testable in A's folders. |
| 59 | Extraction | OCR text whose totals don't add up gets one vision re-read; the read with fewer arithmetic problems wins (OCR on a tie), both cached, a warning names the one used. Born-digital PDFs are never re-read | A misread digit is the usual OCR failure and the image settles it; a total that's wrong on the document stays wrong however often it's read. |
| 60 | Extraction | Prompt v4: currency from the totals line, else from wherever the document states it in words; `$` alone stays "not stated" (CAD assumed for Canadian vendors, with a warning) | Unseen layouts write "Canadian dollars" in prose; guessing from `$` alone would hide a real ambiguity. |
| 61 | Extraction | An unknown tax label with a zero amount is dropped silently; with a real amount it still warns | "Sales tax $0.00" on a US invoice isn't a tax; an unknown fee with money in it must reach a human. |
| 62 | Testing | Real model output recorded per file (`tests/fixtures/raw`) and replayed through the real pipeline offline; expectations for all 56 files derived from the PDFs, not from our output | Tests stay free and deterministic while still exercising what the model really returns. |
| 63 | Extraction | Every re-check after an edit is an audit event (`bill.rechecked`, actor `system`); `draft_json["as_extracted"]` is written once | The snapshot stays traceable: what was read, and every recomputation after it. |
| 64 | Coding | Learned codings are a cache of `bill_lines`, replayed at start-up | One source of truth in the database; process memory is only for speed. |
| 65 | API | Approvers can't read intake emails or files, like `/intake/emails` and `/intake/items` | Approvers act on bills routed to them; the inbox is the back office's. |
| 66 | Intake | Originals kept content-addressed (`backend/files/<sha256>`); served with a type sniffed from the bytes, only for hashes an intake item references | Side-by-side review without trusting file names; nothing outside intake can be fetched. |
